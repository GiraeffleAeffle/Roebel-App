# Sovereign Netizen Account — Phase A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the sovereign Netizen Account reachable — flip the claim namespace to `netizen:*`, issue resource-scoped JWT access tokens the signer accepts, fix the `OIDC_AUDIENCE` render defect that would let the signer accept any token, and declare the signer in the Röbel manifest so it can be deployed.

**Architecture:** The keystone (`apps/roebel-id`) mints a JWT access token audience-scoped to the signer's URL, carrying `netizen_class` and `netizen_step_up`. The signer (already built, in netizen_labs) verifies it against the keystone's JWKS. A member's sovereign account is a node-held vault EOA keyed by their existing OIDC `sub`; their thirdweb account is untouched. Two forward-compatibility seams (an `EventSink` for usage metering, a served branding document) are added now because they cannot be retrofitted cleanly.

**Tech Stack:** TypeScript, `oidc-provider` 8.8.1, `jose` 5, `openid-client` 5 (tests), Zod (manifest schema), Node 22.

**Two test frameworks — check which repo you are in.** `apps/roebel-id` (DAO_test) and `apps/ortis` use **vitest** (`describe`/`it`/`expect`). Every `packages/*` in netizen_labs uses **`node:test` + `node:assert/strict`** via `tsx --test test/*.test.ts` — no vitest is installed there. Writing the wrong one fails at import, not at assertion.

**Spec:** [`docs/superpowers/specs/2026-08-11-sovereign-netizen-account-infrastructure-design.md`](../specs/2026-08-11-sovereign-netizen-account-infrastructure-design.md) — Phase A is §4–§6.

- **SIWE statements must stay ASCII** — `siwe@3` enforces the EIP-4361 ABNF.
- **`netizen_step_up` is always present and always `false` in Phase A.** Never omit it; an absent claim could default wrong somewhere.

```ts
/**
 * An optional absolute URL. Validated at boot rather than at first use: an invalid resource
 * indicator does not fail loudly, it makes every token request answer `invalid_target` while
 * /health stays green. Same reasoning as the redirect-URI check added in d9ce3651.
 */
function optionalAbsoluteUrl(name: string): string | undefined {
  const v = process.env[name]?.trim()
  if (!v) return undefined
  let parsed: URL
  try {
    parsed = new URL(v)
  } catch {
    throw new Error(`Invalid ${name}: "${v}" is not an absolute URL (expected e.g. https://signer.example.org)`)
  }
  if (parsed.protocol !== 'http:' && parsed.protocol !== 'https:') {
    throw new Error(`Invalid ${name}: "${v}" must use http or https`)
  }
  return v
}
```

```ts
import { errors, type Configuration } from 'oidc-provider'
import type { Config } from '../config.js'

/**
 * The identity class every human login gets in Phase A. The signer's policy engine reads it
 * (`packages/signer/src/auth.ts`) and understands `citizen` | `agent` | `org`; only `citizen`
 * is minted here. Agent principals are Phase C — plumbed, deliberately not issued.
 */
export const NETIZEN_IDENTITY_CLASS = 'citizen'

/** Access-token lifetime, matching the provider's existing AccessToken ttl. */
export const NETIZEN_ACCESS_TOKEN_TTL = 3600

/**
 * Resource-indicator policy: this keystone mints access tokens for exactly ONE resource, the
 * node's signer.
 *
 * An allowlist rather than a wildcard on purpose. `getResourceServerInfo` is what decides
 * which `aud` a token carries, so accepting any indicator would let a first-party client mint
 * a token audienced at a service of its choosing — and the signer's whole authorization story
 * is that it only honours tokens audienced at itself.
 *
 * Returns `undefined` when no signer resource is configured, which leaves the feature off.
 */
export function buildResourceIndicators(
  config: Config,
): NonNullable<NonNullable<Configuration['features']>['resourceIndicators']> | undefined {
  const resource = config.signerResourceUrl
  if (!resource) return undefined

  return {
    enabled: true,
    // Clients that ask for no resource still get the signer token; there is only one.
    defaultResource: () => resource,
    useGrantedResource: () => true,
    getResourceServerInfo: (_ctx, resourceIndicator) => {
      if (resourceIndicator !== resource) {
        throw new errors.InvalidTarget(`unknown resource indicator: ${resourceIndicator}`)
      }
      return {
        scope: 'netizen',
        audience: resource,
        accessTokenTTL: NETIZEN_ACCESS_TOKEN_TTL,
        accessTokenFormat: 'jwt',
      }
    },
  }
}

/**
 * Claims the signer reads off a verified access token.
 *
 * `netizen_step_up` is emitted as an explicit `false` rather than omitted. The signer treats a
 * missing claim as not-stepped-up today, but an absent field is a fact nobody stated — and the
 * step-up flow that will one day set it true (Phase C) must find the field already on the wire,
 * not introduce it.
 *
 * ID tokens are untouched: they describe a login, not an authorization to act.
 */
export function buildExtraTokenClaims(): NonNullable<Configuration['extraTokenClaims']> {
  return (_ctx, token) => {
    if (token.kind !== 'AccessToken') return undefined
    return { netizen_class: NETIZEN_IDENTITY_CLASS, netizen_step_up: false }
  }
}
```

```ts
/**
 * Usage events: the countable record behind an operator dashboard (MAU, wallets created,
 * sponsored operations).
 *
 * Deliberately separate from `AuditSink`. The audit trail is a compliance record — hash-only,
 * privacy-preserving, and it answers "was this action allowed"; it cannot answer "how many
 * wallets exist". This sink answers the second question and nothing else, so the closed event
 * set below is the whole vocabulary.
 *
 * PRIVACY RULE, binding on any aggregation layer built on top of this: in sovereign mode these
 * events never leave the node. Only a hosted deployment may export, and only aggregates.
 */
import { appendFile, mkdir } from "node:fs/promises";
import { dirname } from "node:path";

/** The closed set of countable actions. Adding a kind is a deliberate act, not a convenience. */
export type UsageEventKind = "account.created" | "message.signed" | "userop.sponsored";

export interface UsageEvent {
  /** ISO 8601 timestamp when the event occurred. */
  at: string;
  kind: UsageEventKind;
  /** The verified token subject the action was performed for. */
  subject: string;
  /** Only meaningful for `userop.sponsored`. */
  chainId?: number;
}

export interface EventSink {
  record(e: UsageEvent): Promise<void>;
}

/** In-memory sink for tests. Unbounded — never wire this into the running service. */
export class MemoryEventSink implements EventSink {
  events: UsageEvent[] = [];

  async record(e: UsageEvent): Promise<void> {
    this.events.push(e);
  }
}

/**
 * Append-only JSONL, one `UsageEvent` per line — the same durability story as
 * `FileAuditSink`: appends only, so a crash mid-write can corrupt at most the newest record,
 * never history.
 */
export class FileEventSink implements EventSink {
  private readonly path: string;
  private dirEnsured = false;

  constructor(path: string) {
    this.path = path;
  }

  async record(e: UsageEvent): Promise<void> {
    if (!this.dirEnsured) {
      const dir = dirname(this.path);
      if (dir && dir !== ".") await mkdir(dir, { recursive: true });
      this.dirEnsured = true;
    }
    await appendFile(this.path, `${JSON.stringify(e)}\n`, "utf8");
  }
}

/** A sink that drops everything — the default when no event sink is configured. */
export class NullEventSink implements EventSink {
  async record(): Promise<void> {}
}
```

**Repo:** netizen_labs

- Produces: `POST /v1/accounts` responds `{ address, created, npub, nostrPublicKey }`. `NodeAccount` gains `npub: string` and `nostrPublicKey: string` as eager properties, alongside the existing lazy `nostrIdentity()` method.

**Why (Max, 2026-08-11):** creating a wallet and then separately creating a Nostr identity is two ceremonies for one act. A member should finish account creation already having both. The npub is deterministically derived from a signature over a fixed message (ECDSA signing is RFC-6979 deterministic), so this stores nothing new and cannot drift from the wallet — it is the same identity expressed twice.

```ts
  // a client never has to run a second ceremony, and the two can never diverge.
  const res = await post("/v1/accounts", {}, token);
  assert.equal(res.status, 200);
  assert.match(res.body.address, /^0x[0-9a-fA-F]{40}$/);
  assert.match(res.body.npub, /^npub1[0-9a-z]+$/);
  assert.match(res.body.nostrPublicKey, /^[0-9a-f]{64}$/);
});

test("the npub is stable across repeated account creation", async () => {
  // Derivation is deterministic (RFC-6979), so an idempotent create must not mint a new
  // identity. If this ever fails, every Nostr note a member signed is orphaned.
  const first = await post("/v1/accounts", {}, token);
```
